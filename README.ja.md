# AI RPGエンジン

決定的なRPGシミュレーションを構築するためのTypeScriptツールキット。ステータスを定義し、モジュールを選択し、戦闘スタックを構成し、コンテンツを作成します。エンジンは、状態、イベント、乱数生成、アクションの解決、およびAIの意思決定を処理します。すべての実行は再現可能です。

これは、完成したゲームではなく、**コンポジションエンジン**です。12個のスターターワールドは例であり、そこから学習して再構築できる、分解可能なパターンです。ゲームでは、エンジンから必要なサブセットを使用します。

---

## これは何なのか

- **モジュールライブラリ** — 30以上のエンジンモジュールがあり、戦闘、知覚、認知、派閥、噂、移動、仲間などをカバー
- **コンポジションツールキット** — `buildCombatStack()`で戦闘を約7行で構成し、`new Engine({ modules })`でゲームを起動
- **シミュレーションランタイム** — 決定的なティック、再生可能なアクションログ、シードされた乱数生成
- **AIデザインスタジオ**（オプション）— スキャフォールディング、批評、バランス分析、調整、Ollamaを使用した実験
- **オプションのオンレジャーレイヤー** — `@ai-rpg-engine/ledger-adapter`は、ゲームのコインと取引可能なアイテムを実際のXRPL **テストネット**トークンで裏付け、チェックポイントで決済します。これは、決定的なコアとは完全に独立しています（オプトイン。これがない場合でも、実行はバイト単位で同一になります）。
- **オプションのビジュアルホスト** — `@ai-rpg-engine/sidecar`にGodot 4クライアント[`ai-rpg-stage`](https://github.com/mcp-tool-shop-org/ai-rpg-stage)を追加。エンジンはまだピクセルを出力しません。ステージは2:1の等角投影の港を描画し、`felt`のオーディオを再生します。占有はゾーンIDのままです。

## これは何ではないのか

- 完成したゲームを 1 本提供するものではありません。今日すぐ `run` で動かせるプレイ可能なスターターワールドを 12 個、例として同梱しており、エンジンは*自分の*ゲームを組み立てるためのツールキットです
- これはグラフィックエンジンではありません。ピクセルではなく、構造化されたイベントを出力します。描画は、ホスト（ターミナルまたはGodot）の役割です。
- ストーリーを自動生成するものではなく、世界をシミュレーションするものです。物語は、そのメカニズムから自然に生まれます。

- **ホストサーフェスはエンジン（v3.8.1）上にあります：** `hash`、`present`、`preview`、`getAvailableActions`、`advanceRound`、サイドカー`listActions`＋保存／読み込み、スタジオ`emit-pack`、JSONパックカタログ、および`ruleProfiles`。GodotのアタッチとJSON`--content`ブートは、もはやCLI内部をコピーして、それらのインターフェースを新たに作成することはありません。
- コアランタイム：ワールドの状態、イベント、アクション、ティック、リプレイ — v1.0 以降は安定版；決定的なバイト単位での同一リプレイ（インスタンスごとのIDカウンター、シード値付き乱数生成器）

- **状態異常（v2.4）：** パッシブなステータス変更が戦闘に影響を与える、確定的なDoT/HoTの効果が一定時間ごとに発生する、深さによって効果が制限される反応型トリガー（棘や反射）
- **プラグインプロファイル — エンティティごとのルール解決（v2.5）：** `might`の戦士と`will`の神秘主義者が、1回の戦闘で互いに戦い、それぞれが独自のデータマッピングを通じてステータスを読み取ります。`RuleProfile` + `WorldState.ruleProfiles` + `EntityState.ruleProfileId`；`applyProfile()`はプロファイル（ステータスマッピング、リソースプール、エンティティごとの能力）を付与します。`buildProfile()`、`validateProfileSet()`（重複するIDは拒否されます）、10個の初期テンプレート、および`profile`のCLIコマンド。
- **実際にプレイ可能なループ（`run`、v2.6）：** これはデモ版ではなく、完全なゲームです。敵は独自のAIに基づいて行動します（`aggressive`/`cautious`/`territorial`/`calculating`、現在は6つの基本設定があり、さらに`passive`と`follower`が追加されています）。戦闘は勝利または敗北で終了し、ゲームを保存して再開できます。また、能力や経験値はアクションメニューに表示されます。`run <path>`は、事前に作成したゲームをロードします。見やすいHUDとアクセスしやすいカラー（`NO_COLOR`に対応、TTY非対応）を備えた、洗練されたゲームインターフェースです。
- **AIデザインスタジオは、独自のコマンド（v2.6）として提供されます（`ai`）：** `npm install -g @ai-rpg-engine/ollama` → `ai chat` — ローカルのOllamaモデルを使用して、コンテンツの作成、評価、および調整を行います。
- 統合された意思決定レイヤー：戦闘と能力スコアリングを1つの処理にマージ（`selectBestAction`）
- すべての12個の初期ワールドは、実績のある構成要素である`buildCombatStack()`を使用しています。
- 各スターターAIのチューニングに使用する認知設定API（`cognition: CognitionCoreConfig | false`）
- コンテンツ作成用のタグ分類および検証ツール
- **世界の反応（v2.7）：** 敵を倒すと熱が蓄積し、地域の安全性が低下します。各ラウンドで世界のイベントが発生し、隠された圧力が噂として表面化します（「噂があなたに届きます…」）。噂はエスカレートし、結果をもたらして消えていきます。約30種類の戦闘イベントが、10つの開始地点のいずれかのゾーンにプレイヤーが侵入した際に発生します。各イベントは、事前に決定されたパターンで発生し、より危険な地域ではより多くのイベントが発生し、ボス戦の舞台は保護されます。
- **リターン（再訪）の理由（v2.7）：** 長期間にわたって使用されてきたゲームシステムにおいて、最小限のクエストループを設ける。クエストは特定のトリガーで開始され、キル数、到達地点、進行状況などの目標を追跡し、経験値とアイテムを一度だけ報酬として与える。4つの作成済みのクエスト、**ジャーナル**画面、ラウンドのストーリーにおけるクエストの重要なポイントが含まれる。
- **装備が戦闘に影響を与える（v2.7）：** `equip`/`unequip`は、ステータスレイヤーを通じて実際の数値を戦闘計算式に反映させます。これにより、戦闘コードの変更は不要になり、グラディエーターの三叉戟と網が端から端までテストピンで接続され、命中率のデルタが調整されます。
- **シード値付きの実行（v2.7）：** 新しいセッションを開始するたびに、そのセッションのシード値と、完全に同じ状況を再現するためのコマンドが出力されます。`--seed <n>`は、セッションをバイト単位で完全に再現します。戦闘、抵抗、能力、戦術のロールはすべて、ワールドのシード値を使用します。また、エンディングでは、実際にプレイしたセッション（リアルタイムの状況、プレッシャー、勢力間の関係、プレイヤーのレベルなど）に基づいて結果が決定されます。
- **`buildWorldStack()`（v2.7）：** `buildCombatStack()`の横に配置された、戦略的な構成要素の中核となる部分です。1つのコマンドで、環境、勢力、噂、地区、敗北の影響、遭遇、クエストなどをまとめて設定できます。さらに、**ディレクターズ・レジャー**と呼ばれる戦略画面、`AI_RPG_DEBUG=1`シミュレーション検査機能、Continueと同じ権限によって制御される`inspect-save`、そして、出荷時に復元パスで使用されるモジュール保存・移行機能が含まれます。
- **生きた経済を活性化する（v2.8）：** `createEconomyCore`は、各地区に経済圏を確立し、各ラウンドでその経済圏を活性化させます。新しい`sell`の動詞は、`computeItemValue`（希少性／派閥／起源／密輸品）を通じて略奪品に価格をつけ、地域の供給を調整します。1つのスクリプトで5つのシステムが起動し、v2.7で闇取引が行われました。これには、ディレクターの「マーケット概要＋派閥」スコアリング、終盤の商人王アークと崩壊トリガー、および4種類の経済的圧力が含まれます。**このサイクルでは販売のみ**（購入→v2.9）。
- **仲間（v2.8）：** `recruit`動詞はパーティーを編成します。つまり、仲間は、ステータス、タグ、勢力などを持って、あなたと共に戦います。仲間の戦闘は、戦闘システムの迎撃メカニズム（`isAlly`が設定されるまでは非表示）を利用します。仲間は士気に反応し、離脱することもできます。また、7人の待機中の仲間を仲間に加えることができます。これは、最終段階の「仲間」の紹介、パーティーのターゲット設定、NPCの行動目標、好意クエスト、そしてディレクターの「パーティー」セクションに繋がります。**このサイクルにおける受動的な迎撃**（独立したターン→v2.9）
- **ディレクターは、ボード全体（v2.8）を確認します。** 具体的には、新しい「EQUIPMENT Ledger」セクション（CLI→機器の来歴依存関係の背後）、ディレクターによる「DIRECTOR'S SUMMARY」の最終予告編、ライブで情報を送信するプロデューサーからの「MARKET OVERVIEW + PARTY」セクション、そして最終回の「DISTRICTS」セクションにおける地区の安定性と経済状況です。
- **経済のもう一方の側面（v2.9）：**ある動詞（`buy`）が、一連の流れを完結させる。 — 地域ごとに、供給カテゴリのレベルで区切って提供される商品在庫（供給レベルが在庫補充の合図となります）。価格は、同じパイプライン`computeItemValue`を通じて決定されます。 `sell`に加えて、買いと売りのスプレッドが加わるため、完全にリスクのない往復取引は存在しません。 そして、クラフト機能が活性化されます。`createCraftingCore`は、作成したレシピテーブルに対して、`salvage`/`craft`/`repair`/`modify`を登録し、これまで非表示になっていた「ディレクターの素材とレシピ」セクションを有効にします。
- **仲間は順番に交代する（v2.9）：** v2.8の受動的迎撃フロアが天井になる。新たに加わった仲間は、以前は使用されていなかった`selectBestAction`のアドバイザーを通じて、各ラウンドで独立して行動する。役割ごとに戦闘の傾向が異なり、戦士と学者は異なる戦い方をする。仲間同士が互いに迎撃し合い、パーティー全体のHPはディレクターのPARTYラインに表示される。仲間がいないパーティーは、データが完全に同一のまま（空のパーティーゲートは、シード0の過去の記録を保持する）。
- **エンドツーエンドで接続されたソーシャルレイヤー（v2.9）：** 4つの重要な動詞（`bribe`、`intimidate`、`petition`、`seed`（噂））を使用して、実際の評判、警告、関心を集めるグローバル情報を書き込み、すでに読まれている価格や勢力間の関係を取引し、さらに`seed`でプレイヤーの噂モジュール全体と、ディレクターが作成した「あなたに関する噂」セクションを活性化させます。これらに資金を提供する「影響力経済」も連携しています。つまり、特定の機会を達成すると、常に語られてきた影響力が得られるため、これらの動詞はゲーム内で実際に獲得できるようになります。
- **機会、完全なライフサイクル（v2.9）：** 各ラウンドごとに、現在のゲーム世界の状況に基づいて評価される契約、報酬、好意などを提供するシステムです。まず、あなたは`accept`を実行し、次に`complete`または`abandon`を実行します。いずれかを期限内に実行しないと、ペナルティが発生します（期限切れによる影響）。また、好意を完了すると、そのキャラクターの士気が向上します。ゲーム終盤の権力増大と商人王の物語は、実際にあなたが解決した機会を反映します。

**不完全または未完成な点:**
- AIによる世界構築スタジオ（Ollamaレイヤー）は、シミュレーションコアよりもテストが少ないため、ローカルのOllamaデーモンが必要。これは完全にオプションであり、エンジンと`run`ループにはネットワークは不要。
- ナレーション/オーディオスタックは、決定的なオーディオコマンドを生成するが、**端末オーディオバックエンドは存在しない**。つまり、`run`で音が再生されることはない。Godotステージは、実際に`felt`キューID（ミキサー+オプションのTTS）を再生する最初のホストである。オーバーレイ効果音は、ゾーンの基本音を置き換えてはならない。
- マルチプレイヤー（1つの世界を共有する2人の人間プレイヤー）は**実装されていない**。これはネットワークレイヤーであり、意図的にスコープ外である。現在のプロファイルは、単一のコントローラーを対象としている。
- `replay --replay`は、再シミュレーションの代わりに保存データを復元する。そして、v2.9の後に、それが**決定的な**方向である。これは一時的なものではない。`Engine.serialize()`はすでに、完全な状態のスナップショットであることが証明されている。再シミュレーションを行う場合、アクションログの外にあるワールドティック/エンカウンターの状態を追跡する必要がある。v2.9は、その証明された復元パスで、複数のチェックポイント保存スロットを実装する。真のイベントソースによる再シミュレーションは計画されていない。
- v3.1は、v3.0の3つの名前付き天井を閉じた。これには、ジャンル固有の**初期供給量**、ジャンル固有の*修理*レシピ、および`deny`/`bury-scandal`メニューの表面が含まれ、これらはすべて現在実装されている。残っている唯一の天井は、新しいジャンルの修理レシピに、作成者が設定した`statDelta`（小さなステータスボーナス）が含まれていることである。これは、`resolveRepair`ではまだ適用されない。修理は*復元*であり、`modify`は*アップグレード*であるため、修理をアップグレードとして扱うことはコード内でマークされ、**v3.2/v3.3に遅延**される。これは、意図的なメカニズムであり、静かで不活性なフィールドではない。そして、`obligation-exists`には、1つの作成されたデモ（ブラザー・アルドリック）が含まれている。この条件は、コンテンツ作成者がより多くのダイアログを制御できるように、ライブになっている。
- ドキュメントは豊富だが、すべてのハンドブックのページが最新のAPIを反映しているわけではない。

## インストールとプレイ

スターターをプレイするか、端末から独自のゲームを構築する。

```bash
npm install -g @ai-rpg-engine/cli

ai-rpg-engine run                    # pick a starter, build a character, play
ai-rpg-engine create-starter my-game # scaffold a new game you can edit and run
ai-rpg-engine run ./my-game          # run a game you scaffolded
```

`run`ループは、実際のターンベースのセッションである。敵は独自のAIプロファイルに基づいて行動し、アビリティと経験値はメニューに表示され、保存して再開でき、戦闘は勝利または敗北で終了する。すべてのゲームは決定論的であり、再生可能である。

オプションとして、AIデザインスタジオを独自のコマンドとしてインストールできる。

```bash
npm install -g @ai-rpg-engine/ollama
ai chat                              # scaffold, critique, and balance content
                                     # against a local Ollama model (see Ch. 36)
```

スタジオは、ローカルの[Ollama](https://ollama.com)デーモンと通信する。まず、`ollama serve`と`ollama pull qwen2.5-coder`を実行する。これは完全にオプションであり、エンジンと`run`ループにはネットワークは不要。

コンテナイメージは、CIおよびサンドボックス化された実行のために、GHCRに`ghcr.io/mcp-tool-shop-org/ai-rpg-engine`として公開される。

## クイックスタート

コードで独自のゲームを構築することを希望する場合、エンジンをモジュールから構成する。

```typescript
import { Engine } from '@ai-rpg-engine/core';
import { buildCombatStack, traversalCore, statusCore, createDialogueCore } from '@ai-rpg-engine/modules';

// Define your stat mapping
const combat = buildCombatStack({
  statMapping: { attack: 'might', precision: 'agility', resolve: 'will' },
  playerId: 'hero',
  biasTags: ['undead', 'beast'],
});

// Wire the engine
const engine = new Engine({
  manifest: myManifest,
  modules: [statusCore, ...combat.modules, traversalCore, createDialogueCore(myDialogues)],
});

// Submit player actions
engine.submitAction('attack', { targetIds: ['skeleton-1'] });

// Submit AI entity actions
engine.submitActionAs('guard-captain', 'attack', { targetIds: ['player'] });
```

完全なワークフローについては、[構成ガイド](site/src/content/docs/handbook/57-composition-guide.md)を参照するか、新しいスターターを構築する。

```bash
npx @ai-rpg-engine/cli create-starter my-game
```

## XRPL台帳アダプター（オプション）

`@ai-rpg-engine/ledger-adapter`は、ゲームの**プレイヤーが所有する取引可能なレイヤー**（`coin`の残高と消費可能なインベントリ。これは、`trade-core`の`buy`/`sell`の動詞によってすでに移動される）を**XRPLテストネット**にバインドする**オプションの**パッケージである。これにより、これらのアセットは、実際のオンチェーンのトークンによって裏付けられ、チェックポイントで決済される。アダプターが存在しない場合、それは今日出荷されるオフラインエンジンそのものである。

**決定論の不変性（最も重要な点）。** アダプターは*サイドチャネル*であり、シミュレーションの一部ではない。

- **決定論的なティック内では決して呼び出されない**。**チェックポイント**（保存、町/市場への入り口、チャプターの区切り）でのみ呼び出される。
- `@ai-rpg-engine/core`または`@ai-rpg-engine/modules`のいずれにも、アダプターをインポートするコードはない（エンジンへの唯一の依存関係は、コンパイル時の`import type`である）。
- **アダプターの有無にかかわらず、実行はバイト単位で同一である。** ファイアウォールテストでは、実際の`starter-pirate` `createGame()`の商人ループを、アダプターが有効になっており、チェックポイントで決済される2つのエンジンで実行し、2つのワールドが完全に等しいことを確認する。シード0のリプレイは変更されない。

**統合レベル — ゲームは、その設計に応じて、アダプターをどの程度深く組み込むかを決定する。** ファイアウォールは*決定論*の境界であり、統合を禁止するルールではない。上記の不変性は、すべてのレベルで保持される。

| レベル | アダプターに依存するもの | 適合性 |
|-------|-----------------------------|------|
| **L0 — External observer** | ゲーム内には何も依存しない。アダプターは、チェックポイントで外部から接続され、ゲームはそれを認識しない。 | 既存のゲームへの後付け（出荷される海賊デモ）。 |
| **L1 — ゲーム駆動型のチェックポイント** | ゲーム自体の保存/町/メタプログレッションフローが、定義された時点でアダプターを呼び出す。 | ゲームが、意図的な台帳の瞬間を必要とする場合。 |
| **L2 — Ledger-native design** | ゲームの経済またはアイデンティティは、オンチェーンの所有権（永続的な発行者、実際の市場）を中心に設計されている。 | 台帳を重視した商人ゲーム。 |

リプレイを安全に保つための区別は、「どのパッケージがアダプターをインポートするか」ではなく、「呼び出しがティック内にあるかどうか」である。ゲームパッケージは、アダプターを自由にインポートして駆動してもよいが、すべての呼び出しが、シード駆動のリプレイループの外にあるチェックポイントで行われる必要がある。

**3つのプレイモード。** `offline`（デフォルト — チェーンなし、出荷されるエンジン）· `ledger`（テストネットの残高によって裏付けられたコイン/アイテム、チェックポイントで決済）· `diary`（オフラインでプレイし、次に実行の状態ハッシュを台帳に固定して、改ざん防止のレシートを作成する）。

**台帳に記録されているもの。** `coin` → トラストライン上の発行通貨の借用証；
消耗品 → 交換可能なトークン；チェックポイントにおける純取引量の差 → XLS-85トークンエスクローによる決済。ユニークな装備は XLS-20 NFT として出荷され、（v3.3）、遺物の成長により、変更可能な NFT のメタデータが XLS-46 `NFTokenModify` を介してその場で更新される。これは v3.4 の時点から実際のゲームプレイによって駆動される。抽象的な地区経済（`economy-core`）は *変更されない* — 純粋なシミュレーションのまま維持される。

**安全対策。** テストネットのみで使用。コード内に「メインネットでは不可能」という構造的なガード（設定フラグではない）を設ける。ウォレットのシードは、Git で無視される secrets 側のファイルに保存され、決してセーブファイルには保存されない。決済はべき等であり、再試行パス上では安全にリソースを保護する。証明は、**実際のオンチェーンメモ**（エンジン独自の文字列ではない）を検証する。チェーンにアクセスできない場合、実行は単に継続され、*アンカーされていない*とマークされる。

**実証済みの稼働。** 実際の `starter-pirate` マーチャントの実行 — サーベルを販売し、大砲の砲弾を購入する — トークンエスクローを介して XRPL テストネットで決済を行い、次に `reconcile()` が、エンジン内の経済に対して、台帳上の残高とメモを確認する（すべてのトークンに対してリソース保護が有効）。台帳は、エンジンとは異なるシステムファミリーであるため、エンジンはそれを偽装することはできない。整合性は、真の外部検証者によって行われる。テストネットのみで使用。アセットはゲームスコープのレシートであり、有価証券ではない。

## 戦闘システム

5つのアクション（攻撃、防御、離脱、態勢、位置変更）、4つの戦闘状態（防御、体勢を崩す、無防備、逃走）、4つの交戦状態（交戦、防御、後方、孤立）。3つのステータス次元がすべての計算を駆動するため、素早い剣士は、重装の戦士や冷静な歩哨とは異なる動きをする。

AI 相手は、統一された意思決定スコアリングを使用する。戦闘アクションと能力が、単一の評価で競い合い、設定可能な閾値により、些細な能力の乱用を防ぐ。

パックの作成者は、`buildCombatStack()` を使用して、ステータスマッピング、リソースプロファイル、およびバイアスタグから戦闘を構成する。 [戦闘の概要](site/src/content/docs/handbook/49a-combat-overview.md) および [パック作成者ガイド](site/src/content/docs/handbook/55-combat-pack-guide.md) を参照。

## 能力

ジャンルに特化した能力システム。コスト、ステータスチェック、クールダウン、および型付きの効果（ダメージ、回復、ステータスの付与、浄化）を持つ。ステータス効果は、抵抗/脆弱性のプロファイルを持つ 11 タグのセマンティック語彙を使用する。AI は、自己/AoE/単一ターゲットのパスを認識してスコアリングする。

```typescript
const warCry: AbilityDefinition = {
  id: 'war-cry', name: 'War Cry', verb: 'use-ability',
  tags: ['combat', 'debuff', 'aoe'],
  costs: [{ resourceId: 'stamina', amount: 3 }],
  target: { type: 'all-enemies' },
  checks: [{ stat: 'nerve', difficulty: 6, onFail: 'abort' }],
  effects: [
    { type: 'apply-status', target: 'target', params: { statusId: 'rattled', duration: 2 } },
  ],
  cooldown: 4,
};
```

### 目的：プラグインプロファイル

エンジンの最終的な目標は、**ユーザー定義のプロファイル**です。これは、任意のゲームにスロットインできる、ポータブルなバンドルです。プロファイルは、ステータスマッピング、リソースの動作、AIのバイアスタグ、および能力を、1つのインポート可能なユニットにパッケージ化します。v2.5では、1つの世界内のエンティティはそれぞれ独自のプロファイルを保持し、エンティティごとに戦闘を解決できます。`might`のファイターと`will`のミスティックが1つのパーティーを共有し、それぞれが独自のプレイスタイルを持ちます。

スキーマ、`applyProfile`ローダー、エンティティごとの能力解決、およびクロスプロファイル検証はすべてリリースされています。残っているのは、2人の*人間*プレイヤー（単なる2つのエンティティではなく）が1つの世界を共有できるようにするマルチプレイヤーです。これはネットワークレイヤーです。[プロファイルロードマップ](docs/profile-roadmap.md)と[feature-architecture.md](docs/feature-architecture.md)を参照して、設計を確認してください。

## 哲学

AI RPGエンジンは、次の3つのアイデアに基づいて構築されています。

1. **決定論的な世界** — シミュレーションの結果は再現可能でなければなりません。
2. **証拠に基づいた設計** — 世界のメカニズムは、シミュレーションを通じてテストされるべきです。
3. **AIはアシスタントであり、権威ではありません** — AIツールは、設計の生成と批判を支援しますが、決定論的なシステムに取って代わるものではありません。

完全な説明については、[PHILOSOPHY.md](PHILOSOPHY.md) を参照してください。

## セキュリティ

コアエンジンは、**ローカルでのみ動作するシミュレーションライブラリ**です。テレメトリ、ネットワーク、秘密情報は一切使用しません。保存ファイルは、明示的に要求された場合にのみ、`.ai-rpg-engine/` に保存されます。2つの**オプション**のレイヤーがアウトバウンドパスを追加しますが、それらを呼び出した場合にのみ有効になります。

- AIレイヤー（`@ai-rpg-engine/ollama`）は、**ローカルの**Ollamaデーモンと通信します。オプションの機能（RAG用、`webfetch`）は、SSRFガードによって制限されており、ループバック、リンクローカル、CGNAT、クラウドメタデータ、およびそれらに相当するもの（IPv6-tunnelled）へのアクセスをブロックします。
- レジャーレイヤー（`@ai-rpg-engine/ledger-adapter`）は、**XRPLテストネット**に接続します。ただし、テストネットのみです。コードで実現不可能な構造的なガード（設定フラグではありません）により、構築時にテストネット以外のホストは拒否されます。ウォレットのシードは、Gitで無視される秘密情報コンテナに保存され、決して保存ファイルには保存されません。また、決定的なコアはアダプターをインポートしません。

詳細については、[SECURITY.md](SECURITY.md) を参照してください。
